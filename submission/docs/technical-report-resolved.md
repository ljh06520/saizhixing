## 摘要

我们把赛知行做成一个准备比赛的工作区。参赛同学可以先导入通知，再查报名条件、核对两份资料的差异，最后把找到的要求整理成提交清单。问答的引用可以回到文档原文，日期有冲突时会把两份来源留在页面上。

应用采用Next.js、React、TypeScript、IndexedDB和PDF.js。默认使用本地词法检索及规则解析，可选DeepSeek结构化提取与受限工具调用。模型事实采用逐字摘录合同，不对任意转述宣称语义验证。

当前自动验收9组通过，确定性测试54项通过。11月17日原浏览器回归57/59通过，两项缺陷经修复后完成单列8项针对性复测。历史模型对照与本轮测试分别归档，不合并成通用准确率。作品可从公开仓库本地复现。最终视频与官方提交仍需完成。

# 01 项目概述
## 问题与目标

选题时，我们从准备作品类竞赛的几个实际问题入手。报名通知可能写了人数和组别，提交说明另写了 PDF 页数，补充通知还可能改日期。把这些内容汇总成一份清单之前，学生得先确认每条要求来自哪里，适用哪个阶段。

赛知行聚焦“导入资料、审阅规则、核对条件、追溯冲突、准备材料”的连续流程。目标是使重要结论可回到原文，使不确定性可见，使准备任务能够被勾选与导出。

## 主要输出

- 证据问答：检索当前工作区和阶段，返回带来源的原文摘录。
- 条件核对：以已识别的人数范围和组别条款辅助判断。
- 冲突提示：并列展示同范围规则差异，不自行替用户裁定权威版本。
- 材料清单：合并重复要求，区分可选项，保存自查与来源。
- 有限预检：检查README关键词、PDF页数和可读取的视频参数。

## 适用边界

本系统是准备助手，不是官方资格认证系统。不会自动报名、缴费或提交，不保证材料获得认可或作品获奖。资料的真实性与时效性由用户结合官方通知核实。

价值判断来自任务分析与开发者测试，尚未开展独立用户试用，不报告满意度、实际节省时间或市场收益。

# 02 需求与任务边界
## 输入、输出与约束

我们把需求拆成几个评审可以亲手操作的问题。比如改一次团队人数、打开一处日期冲突，或者选一份 PDF 看页数。每项都能对应到明确的输入、界面结果和人工核对环节。

| 用户任务 | 实现行为 | 结果边界 |
| 能否按人数条款报名 | 读取范围并比较画像人数 | 不等于全部资格通过 |
| 两份通知日期不同 | 显示数值及双方原文 | 不默认新上传文件优先 |
| 需要提交哪些材料 | 解析要求、标记可选、去重 | 不补写未说明要求 |
| 文件参数是否达标 | 读取支持的属性 | 不审查内容质量 |
| 回答有没有依据 | 引用回到存储原文 | 不认证资料为官方文件 |

## 可用性要求

核心流程应能连续完成。资料与状态刷新后恢复。不同工作区独立。无模型时本地能力仍可使用。输入和文件失败时应给出原因，不能把空白、乱码或无法读取的材料算作成功。

## 不纳入本版的能力

不提供扫描件OCR、向量数据库、跨设备同步、多人账号权限、自动采集所有官方通知或赛事自动提交。上述能力未写入本版成果宣称。

# 03 使用流程与人机分工
## 五步准备流程

1. 创建赛事工作区，设置名称、年份和准备阶段。
2. 导入通知，检查文本、来源、适用组别和版本关系。
3. 填写学历、学校类别与人数，审阅规则及条件依据。
4. 打开候选冲突，核对原文。必要时确认明确的替代关系。
5. 生成清单，预检支持的材料属性，勾选并导出自查记录。

## 三方职责

我们把判断交给适合做这件事的一方。模型开启后可以从复杂段落里挑规则候选，也可以选工具查证据。人数上下限、日期和引用位置由代码检查。哪份通知有效、例外是否适用于本队，最终由参赛者核对。

## 不确定性是结果的一部分

“信息不足”“来源冲突”“待确认元数据”“未检查”“用户已自查”含义不同。系统保留这些状态，避免把未发现问题解释为所有条件满足。

演示通知始终标注来源。内置摘录未经官网核验。独立测试通知明确标注合成资料，不将测试日期、奖项比例或人数当作官方要求。

# 04 系统架构
## 本地优先的Web应用

Next.js App Router提供页面和API，React与TypeScript组织交互，IndexedDB保存工作区。资料解析与材料属性预检在浏览器中进行。问答与规则分析向本机服务提交受校验快照。

| 模块 | 主要责任 | 关键实现 |
| 界面与交互 | 工作台、消息、弹窗、工作区操作 | app/page.tsx |
| 业务面板 | 元数据、规则审阅、材料预检 | CompetitionPanels.tsx |
| 检索及规则 | 排序、适用规则、冲突与清单 | lib/rules.ts |
| 快照与引用 | 类型、原文及摘录一致性 | snapshot.ts / answer.ts |
| 本地持久化 | 工作区保存及旧版迁移 | workspace-store.ts |
| 模型开关 | 显式启用、模型名与端点 | model-config.ts |

## 取舍

我们采用浏览器存储加本机服务的结构。评审克隆仓库后就能先查看资料、跑规则和导出清单。需要看模型效果时，再接上 DeepSeek。这减少了部署和账户配置的工作，也限制了目前的跨设备协作能力。

本地隔离降低了工程复杂度，同时不提供多人认证和跨实例授权。部署到公网前需要另行设计访问控制与运行保护。

# 05 工作区、数据与版本
## 数据关系

| 对象 | 主要字段 | 用途 |
| Workspace | id、name、year、documents、profile、stage | 一项赛事的资料和状态容器 |
| SourceDocument | id、text、stage、year、group、source | 原文与适用范围 |
| 版本与页信息 | version、supersedes、pages、metadataConfirmed | 内容定位及替代确认 |
| Rule | kind、value、quote、conditions、min/max | 可审阅规则及原文 |
| Evidence | documentId、version、start/end、page | 消息到原文的定位关系 |

## 版本策略

我们用内容指纹区分同一份资料的不同正文。规则或要求改动后，证据和勾选状态需要按当前资料重新核对。替代关系由用户确认，导入得晚的通知会先和原通知一起保留供比较。

## 持久化与迁移

IndexedDB从旧current记录迁移至library-v2，保留旧记录作为备份。读取失败提示恢复，不主动删除旧资料。自动存储测试覆盖迁移。本轮浏览器验证覆盖新版刷新恢复，尚未完成旧数据库真实浏览器迁移专项。

资料按浏览器来源保存。不同端口和设备不共享，清除站点数据可能导致本地资料丢失。导出清单不等于完整数据库备份。

# 06 文件解析与证据定位
## 输入边界

TXT和Markdown单文件不超过2MB。文本型PDF不超过10MB、100页。每个工作区最多20份文档、30万字。服务端单份文本快照另限制20万字，超过边界的输入不能继续模型流程。

## PDF与文本处理

文本按支持的编码读取。PDF.js逐页提取文本，保留页码。缺少足够可提取文字、加密或损坏的PDF会报错。worker由predev/prebuild复制到本地public目录，不依赖外部CDN。

## 定位与完整原文

片段关联文档ID、内容指纹和字符范围。PDF同时保留页码。证据弹窗展示存储的完整原文与高亮，用户可以核对实际位置，而非只查看模型重述。

复测资料导入时，我们准备了两页有文字的 PDF，把要找的测试句子放在第2页。点击引用后，弹窗显示第2页和字符范围。另用空文件、超限文本、CSV、扫描空白和加密 PDF 检查错误提示。

## 局限

多栏、复杂表格和阅读顺序可能影响提取。本系统不执行OCR，不保证恢复所有版式语义。首次PDF模块加载等待较长的现象已记录，未据此生成性能结论。

# 07 中文词法检索
## 检索流程

只接收当前工作区的快照，先排除已确认被替代的文档，再保留当前阶段和通用阶段。年份、组别和条件参与规则比较，但不能将其描述为词法检索已具备完整语义范围过滤。

中文词元、英文数字及少量问题扩展构成查询特征。BM25式评分使用词频、逆文档频率和长度归一化。实现参数k1为1.2、b为0.75，分数大于0.15的结果按分数选取前6个。

## 旧版对照

我们保留了原来的二元词匹配程序，使用同一批资料、同样的题目比较检索。这样可以直接看两套检索各漏了哪一道题。结果和后续单题复测见第19页。

检索结果是候选证据，不是答案正确性的保证。同义表达、隐含条件和跨片段关系仍可能遗漏。没有命中时提示补充资料或调整问题。

## 技术口径

本项目没有embedding和向量数据库，也没有训练专用模型。问答链可称为基于检索证据的模型增强流程。默认无Key模式仅进行本地检索，不称为模型生成。

# 08 结构化规则分析
## 模型与本地两条路径

启用模型时，POST /api/analyze使用结构化schema提取team、group、deadline、award、material五类规则。否则直接使用本地解析器。两条路径都保留quote和文档关系。

| 检查层 | 实际检查 | 仍需人工处理 |
| 类型结构 | 枚举、长度、数量与字段格式 | 自然语言是否理解完整 |
| 资料对应 | 文档存在、原文包含摘录 | 来源是否官方有效 |
| 范围与数值 | 年份/阶段匹配、min不大于max | 复杂例外与组合条件 |
| 规则审阅 | 修改字段、撤销与重新确认 | 最终报名资格认定 |

## 规范化与确认

规则页里，模型抽出的条目先进入待审阅状态。如果一句通知可以用本地解析器读出人数或日期，我们会用解析结果统一格式。用户仍可以打开原文，修正适用范围或漏掉的条件。

## 条件计算边界

人数比较使用规则的实际上下界。元数据未确认、规则缺失或来源冲突时不给出确定满足。组别输出侧重适用条款，学历、学校和例外条件未被完整覆盖时需人工核实。

结构和摘录检查不能证明所有语义正确，不对任意赛事规则宣称完整提取率。

# 09 冲突检测与版本确认
## 比较前提

在同一工作区内，比较规则的年份、阶段、组别、主题和条件。不同组别或阶段的不同要求不应简单视为冲突。系统重点覆盖人数、日期和奖项比例等已识别指标。

## 合成测试案例

| 场景 | 原文差异 | 浏览器观察 |
| 同范围补充通知 | 截止18日 / 19日。比例20% / 25% | 形成2项候选冲突 |
| 改为其他阶段 | 补充通知从省赛改为国赛 | 省赛候选冲突变为0 |
| 恢复同一阶段 | 补充通知重新确认省赛 | 候选冲突恢复为2 |
| 确认明确替代 | 新通知替代旧通知 | 旧通知退出比较 |

我们用自己编写的两份测试通知验证这一流程。把补充通知改成国赛，省赛冲突从两项降到零。恢复省赛后又出现两项，从界面就能看出阶段设置有没有生效。

## 展示方式

冲突列出双方数值及原文入口，让用户核对完整上下文。确认替代不等于系统认证来源权威。缺少替代依据时保持待确认。

“未检出冲突”表示当前覆盖的规则没有发现差异，不能证明全部规则一致，也不能保证资料不存在遗漏。

# 10 受限工具调用
## 模型可用的工具

| 工具 | 参数 | 返回内容 |
| search_sources | query，最长1000字符 | 当前范围候选证据 |
| compare_rules | 空对象 | 已识别规则的候选差异 |
| check_eligibility | 空对象 | 人数及组别核对依据 |
| build_checklist | 空对象 | 材料条款和来源 |

工具参数经Zod校验，返回值由确定性函数生成，证据收集后再进行回答摘录校验。工具不能读取任意文件、访问其他工作区数据库或执行正式提交。

## 步数与执行记录

普通模型问答最多4步，由模型选择实际调用顺序。展示实际名称、摘要和耗时，不模拟调用，也不展示内部思维链。模型评测为控制调用量，使用独立评测模式，禁用自动工具选择，不等同完整工具链评测。

浏览器回归时，我们发现连续提问会把上一轮工具记录留在面板里。我们改成按当前消息 ID 筛选日志，同时保存旧回答各自的证据。复测第二轮时，面板只显示第二轮的结果，第一轮的原文链接也能打开。

## 默认本地模式

无Key模式只展示实际本地检索记录，不将其包装为Function Calling。历史真实工具执行证据与可选模型能力另行归档。

# 11 引用校验与回答控制
## 引用关系

用户消息ID关联本轮证据，回答中的编号映射到证据数组。证据关联文档ID、内容指纹、字符位置或页码。服务端校验快照内部一致性，浏览器只为已映射证据提供跳转。

## 核对模型摘录

我们要求模型输出一个事实列表，每条包含证据 ID 和从该片段中连续摘取的文字。服务端逐条核对，再把这两部分组装成带编号的回答。页面最后提供独立的核对建议。

编号不存在、摘录不在证据中或输出格式异常时，退回可核对的原文片段。不允许通过无依据补写日期、人数或页数来完善答案。

## 能保证与不能保证的内容

| 可检查 | 不可据此保证 |
| ID是否属于本轮证据 | 文档是官方真实通知 |
| 摘录是否连续存在 | 整体问题获得完整回答 |
| 快照版本是否匹配 | 所有例外条件均被理解 |
| 引用能否定位原文 | 任意转述语义完全正确 |

引用检查主要保障可追溯与原文一致，不能称为消除幻觉或完整语义蕴含验证。用户仍需对照来源和适用条件。

# 12 材料清单与有限预检
## 清单生成

从当前及通用阶段材料规则生成条目，按去空白后的要求文本去重，显式可选条款标注可选。每项保留代表来源。相似改写和复杂联合要求不保证完全合并。条款或元数据变化时要求重新自查。

| 材料 | 实际检查 | 不检查 |
| README文本 | 项目、架构、运行、团队关键词 | 说明质量和代码真实性 |
| PDF | 可读取性与页数 | 论述、原创性、版式质量 |
| 视频 | 浏览器可读的时长与宽高 | 音轨、普通话、讲解内容 |

本版预检按演示赛事配置阈值：PDF不超过30页。MP4为300-480秒且至少1920×1080。它不是从任意赛事通知自动推导的通用标准。

## 实际测试

测试时，我们把2页和31页的 PDF 分别放进预检，前者通过，后者提示超出页数。视频测试也用了两份参数相反的合成文件。301秒、1920×1080的文件通过，5秒、640×360的文件未通过，损坏文件则显示未检查。

勾选仅表示用户自查，不等于预检通过或官方接收。导出Markdown包含要求、来源、勾选、可选项和候选冲突，便于团队分工。

# 13 前端工程与交互
## 界面组织

工作台展示资料、冲突和准备进度。资料页负责导入与元数据。问答页组织消息及引用。规则页提供审阅。清单页记录自查和预检。CompetitionPanels承载主要业务面板，页面级状态仍集中于Home，后续可继续拆分。

## 工作区操作

赛事创建与编辑采用应用内表单。空名称和不合理年份会提示。删除工作区、资料或清空资料前使用自定义确认框，取消不执行操作。

# 14 数据保护与接口约束
## 数据流与权限

我们只让用户填写学历、学校类别和人数，用来核对已有条件。默认模式下，消息和资料快照交给本机 API 处理。打开模型开关后，问答和规则分析才会向模型供应商发送各自所需的数据。

显式模型模式会把问题、必要画像和证据发送给供应商。AI规则分析发送当前资料文本。配置从服务端环境读取，真实密钥不进入公开仓库。

## 保护边界

| 约束 | 当前值或行为 |
| API请求体 | 流式读取，最多1200000字节 |
| 问题 | 最多2000字符 |
| 并发 | 单工作区1个，全局最多8个 |
| 频率 | 单工作区每60秒最多12次 |
| 模型问答 / 规则分析 | 50秒 / 55秒超时控制 |
| 模型工具 | 普通问答最多4步，参数校验 |

## 不可信文档与局限

文档指令不应改变工具权限。防护依靠固定工具范围、参数与快照校验、摘录合同。本轮没有新增提示注入专项浏览器测试，不据此宣称全面免疫。

限流是单进程内存状态，无多人认证与跨实例配额。快照一致性不能证明资料官方真实性，当前本地版不作为已加固的公网生产服务。

# 18 本地安装与复现
## 运行环境

评审可以用 Node.js 22.2 或更高版本配合 pnpm，在本机从仓库复现。以下命令从准备存放项目的目录执行。安装后固定使用仓库里的锁文件。

```powershell
git clone https://github.com/ljh06520/saizhixing.git
cd saizhixing
pnpm install --frozen-lockfile
pnpm verify
pnpm start --hostname 127.0.0.1 --port 3002
```

访问http://127.0.0.1:3002。默认无需创建.env.local。pnpm verify已包含生产构建，pnpm start不能跳过构建直接运行。日常开发可使用pnpm dev，访问终端打印的地址。

## 复现顺序

1. 创建独立赛事工作区并导入演示或合成通知。
2. 确认来源、年份、阶段与组别。填写必要画像。
3. 查询材料要求，点击引用查看完整原文。
4. 审阅规则，验证人数边界及两份通知差异。
5. 对支持文件执行预检，勾选并导出清单。刷新验证恢复。

## 常见问题

找不到verify或start通常是没有进入项目目录。端口占用可更换为3003，但浏览器本地资料不会跨端口共享。构建前先停止开发服务，避免同时使用同一.next目录。

# 19 模型配置与异常恢复
## 默认无Key模式

我们把模型调用设成主动开启。评审首次运行时会看到原文检索和本地规则提取，已有密钥也要配合 AI_ENABLED=true 才生效。页面会根据 /api/status 显示当前使用的模式。

本地模式需要本机Next.js服务。问答呈现原文，不能称为模型理解或模型工具规划。资料、规则核对、冲突与清单仍可使用。

将.env.example复制为.env.local，按需设置下列变量，保存后重启服务。真实密钥只由用户在本机填写。

```dotenv
AI_ENABLED=true
DEEPSEEK_API_KEY=填写自己的真实密钥
MODEL_ID=deepseek-chat
# DEEPSEEK_BASE_URL=https://api.deepseek.com
```

# 20 创新点、限制与展望
## 我们保留了哪些设计

- 证据、规则、冲突和材料准备连接为可追溯流程，而非只返回聊天答案。
- 将信息缺失、范围冲突、未检查和用户自查分别呈现。
- 模型选择摘录与工具，确定性代码负责比较和一致性检查。
- 默认无需模型Key，降低复现门槛。模型增强与本地回退明确区分。
- 实际文件预检只报告可测参数，避免将格式通过当作内容合格。

这些属于应用集成、工程组织和交互设计，不宣称首创RAG、BM25或工具调用算法。

## 现有局限

复杂例外条件需人工修正。词法检索不能覆盖所有同义语义。材料去重主要依赖文本。PDF表格顺序可能失真。本地数据不跨设备。无多人访问认证。摘录校验不能保证回答完整且切题。

## 后续改进

如果继续做，我们会先请实际准备比赛的同学用自己的通知跑一遍，记录哪些条件需要反复修订、哪些问题召回不到材料。等有了这些错误样本，再判断是否值得加 OCR 或语义检索。

潜在价值在于降低阅读通知和整理材料的门槛。市场需求、付费意愿及实际节时尚未验证。
